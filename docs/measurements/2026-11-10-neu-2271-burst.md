# NEU-2271 — Burst before and after (local)

Taken 2026-11-10 (US time; 2026-11-11 ~03:30–03:50 UTC) with `scripts/bench_public_burst.py`, run in the backend
container against the local API (`http://localhost:8000`). "Before" is `src/` as on `main`
(`e149875`: SQLAlchemy's default pool of 5 + 10, a 30 s checkout timeout, and connections held
until the request ends). "After" is the NEU-2271 branch: 10 + 20, a 3 s timeout, public reads
release their connection once the service returns, and a timeout answers 503
(`../specs/NEU-2271-db-pool-fail-fast.md`).

The local stack is not prod. It is one `uvicorn --reload` process on a laptop's Docker VM, with
local data on the shared local Postgres. Only the comparison between runs means anything. Each
configuration ran twice; both runs are shown.

The script reads 200 live person refs and sends GETs alternating between `/people/{ref}` and
`/people/{ref}/events`, keeping a fixed number in flight. Latency is measured client-side, per
request.

## The spec's run: `--requests 600 --concurrency 100`

| | Statuses | p50 | p95 | max | 503 max | OK req/s |
|---|---|---|---|---|---|---|
| Before, run 1 | 600 × 200 | 0.59 s | 3.25 s | 5.96 s | — | 93.1 |
| Before, run 2 | 600 × 200 | 0.42 s | 3.21 s | 5.76 s | — | 101.6 |
| After, run 1 | 599 × 200, 1 × 503 | 0.65 s | 1.83 s | 3.59 s | 3.50 s | 109.7 |
| After, run 2 | 597 × 200, 3 × 503 | 0.66 s | 1.86 s | 3.57 s | 3.57 s | 114.2 |

Against the spec's acceptance criteria, which hold at this load, the spec's suggested one, and
**not** at the 4× load below:

- **Zero 500s.** Met. Neither configuration produced one at this load. Locally, the "before"
  queue never reached the 30 s timeout that failed prod's requests.
- **Every 503 within `db_pool_timeout` + 1 s (4 s).** Met. The slowest was 3.57 s.
- **Successful requests per second at least the before run's.** Met: 110–114 against 93–102.
  The tail moved the most. p95 fell from ~3.2 s to ~1.8 s, and the worst request from ~6 s to
  ~3.6 s, because connections now go back to the pool as soon as the query returns. The median
  rose slightly, 0.42–0.59 s → ~0.65 s. More requests now run their queries at once (30
  connections instead of 15) and share the one event loop, so each takes a little longer, but
  far fewer wait behind a long queue.

## Four times that: `--requests 2000 --concurrency 400`

Past what the spec asked for, to see where the change stops helping.

| | Statuses | p50 | p95 | max | 503 p50 / max | OK req/s |
|---|---|---|---|---|---|---|
| Before, run 1 | 2000 × 200 | 0.42 s | 12.76 s | 17.36 s | — | 114.2 |
| Before, run 2 | 2000 × 200 | 0.49 s | 13.67 s | 18.39 s | — | 106.4 |
| After, run 1 | 1676 × 200, 324 × 503 | 2.33 s | 11.82 s | 15.92 s | 4.24 s / 12.97 s | 85.3 |
| After, run 2 | 1689 × 200, 309 × 503, 2 client errors | 2.51 s | 12.28 s | 16.09 s | 4.29 s / 14.29 s | 83.3 |

At this load the **process** is saturated, not the pool. This is the case ADR-0028's
Consequences describe. Before the change, the 400 in-flight requests all wait in one event loop
and are all served eventually, at a p95 of ~13 s. After it, ~16% are shed as 503s.

- **503s answer late, up to 14 s.** The 3 s timeout runs only from the checkout attempt. A
  request first waits for the saturated event loop to reach its handler. After the timeout, it
  waits again for the loop to send the 503. Neither wait is the pool's, so a shorter
  `DB_POOL_TIMEOUT` would not shorten them.
- **Successful requests per second fell, 106–114 → 83–85.** Part of this is how the benchmark
  works. It keeps a fixed number of requests in flight, and each 503 holds one of those slots
  for ~4 s without serving anything. A crawl that doesn't wait for a reply before sending its
  next request would not be limited this way (asserted, not measured).
- **The median rose sharply, ~0.45 s → ~2.4 s.** Before, most requests got through quickly and a
  long tail waited. After, the wait is spread across all of them.
- **Two client-side connection errors** in one "after" run (`ReadError`, `RemoteProtocolError`).
  Not investigated. They are most likely the dev server dropping connections with 400 in flight.
- **Still no 500s.** The prod incident's failure mode, a 30 s wait and then a 500, does not
  occur in either configuration. Locally, though, the "before" build never reached it either, so
  this run doesn't tell the two builds apart.

This is the saturation ADR-0028's Consequences anticipate. Its two levers still apply, in its
order. First, edge caching of public pages (NEU-2272), which the ADR calls the bigger lever
against crawls. Then, if a process still saturates, more workers, but only after a shared
rate-limit store makes them safe. A different pool size won't help.

## Reproducing

```bash
task shell
python scripts/bench_public_burst.py --requests 600 --concurrency 100
python scripts/bench_public_burst.py --requests 2000 --concurrency 400
```

For the "before" numbers: `git stash push -- src/`, wait for `--reload` to restart, run the
script, then `git stash pop`. Check which pool is live with
`python -c "from upmovies.db import engine; print(engine.pool.status())"` (`Pool size: 5` before,
`10` after).
