# v0.3.0 deploy runbook — backlotter: Undated Film Discovery

**Living document.** v0.3.0 does not ship until the whole project is done, so every ticket that
needs something from a human at deploy time appends here as it merges. On deploy day this file
is the checklist; nothing else should need reconstructing from ticket history.

- **Backend release branch:** `release/v0.3.0` (`upcoming-movies-backend`)
- **Frontend release branch:** `release/v0.3.0` (`upcoming-movies-frontend`)
- **Project spec:** `docs/specs/backlotter-undated-film-discovery-project-spec.md`
- **Last updated:** 2026-08-14, after the top-5 cast tranche was opened in Coolify (see §6)

## 1. What deploys itself, and what doesn't

| Handled for you | Needs you |
|---|---|
| **Migrations.** The prod image's `CMD` runs `alembic upgrade head` before uvicorn, so the one migration in this release applies on container start. | **Coolify env vars** — the prod compose file enumerates env explicitly, so a new var is inert until it's set in Coolify. |
| **Frontend build/deploy** on merge to its main branch. | **The new scheduled task** — Coolify tasks are UI state, not repo state. |
| | **healthchecks.io checks** — created by hand; their URLs feed the env vars. |
| | **Container recreate** — a running container holds the env it was created with. |
| | **Linear ticket status** — moved by the GitHub↔Linear connector; don't touch it. |

## 2. Deploy-day checklist

### Step 1 — Merge the release branches

- [ ] Backend: `release/v0.3.0` → `main` (merge commit, not squash — the release branch's per-ticket commits are the history).
- [ ] Frontend: `release/v0.3.0` → `main`.
- [ ] Confirm the backend release notes / tag reflect what's actually on the branch.

### Step 2 — Create the healthchecks.io check (before the env vars that reference it)

- [ ] New check on healthchecks.io: **`upmovies sweep`**, alongside the existing daily and hourly checks.
  - **Period:** 1 day. **Grace:** ~2 hours — the sweep's own cost envelope is ~45 min today (spec §6.3) and grows with the catalog, so a tighter grace will page on a slow-but-healthy run.
- [ ] Copy its ping URL for `HEALTHCHECK_SWEEP_URL` below.

### Step 3 — Set the Coolify env vars on `upmovies-backend`

Every one of these has a working fallback in `docker-compose.prod.yml`, so the app boots without
them — but the deadman is a no-op until its URL is set.

| Var | Set to | Why | Ticket |
|---|---|---|---|
| `HEALTHCHECK_SWEEP_URL` | the URL from step 2 | The sweep is **not** a stage in the daily chain, so the daily deadman stays green while a dead sweep quietly stops the catalog moving. | NEU-1079 |
| `SWEEP_DORMANCY_DAYS` | leave unset (default `365`) | Deliberate placeholder. M4's tuning ticket sets it from the discovery probe; it's plumbed so that's an env change, not a redeploy. | NEU-1076 |
| `SWEEP_DORMANT_REFRESH_DAYS` | leave unset (default `30`) | Same — the dormant refresh cadence is M4's to tune. | NEU-1078 |
| `INGEST_STALE_RUN_MINUTES` | ~~**`720`**~~ → **unset / code default `30`** | The `720` was a stopgap for the old semantics: cleanup read `started_at`, so at the then-default `15` **any container restart during a multi-hour sweep marked the live run `cancelled`**. NEU-1117 changed what the number measures — cleanup now reads `last_progress_at`, so it bounds **silence**, not total runtime, and a live sweep survives a restart at a much tighter value. Prod runs `30` (~5x the longest legitimate gap, 30x the sweep heartbeat); confirmed on the running container 2026-08-14. No longer needs to exceed the scheduled-task timeout. | NEU-1117 |

### Step 4 — Create the sweep scheduled task

- [ ] Coolify → `upmovies-backend` → Scheduled Tasks → new task:
  - **Command:** `python -m upmovies.pipeline_run sweep`
  - **Cron:** `0 7 * * *`
  - **Container:** the app container (same one the daily/hourly tasks use)
  - **Timeout:** `36000` (the Coolify maximum, 10h) — see below
- [ ] Confirm the existing two are untouched: `0 9 * * *` → `daily`, `0 * * * *` → `hourly`.

**Set the timeout, and set it generously.** Coolify's default killed the first post-flip sweep at
30 minutes on 2026-08-11, mid-enumerate, having written nothing — and left a phantom `running` row
behind, because a killed process never reaches `finalize_run`.

The first sweep after a tranche opens is the worst case it will ever face: the candidate pool is at
its largest, and the enumerate phase fetches **all** ~7,000 seed filmographies before it judges a
single candidate, so nothing is committed for the first ~30 minutes. Budget 1.5–3h for that run,
much less once it reaches steady state.

The hang detector is the deadman healthcheck from step 2, **not** the task timeout — so a generous
timeout costs nothing, while a short one costs the whole run. Tighten it to ~2–3× the observed
duration only after one clean run.

**Ordering:** make every env and task-config change *before* triggering a sweep. A container
recreate is a startup, and startup cleanup acts on runs in flight.

The 2-hour lead on `daily` is load-bearing, not cosmetic: films the sweep admits have to be in the
retrieval index in time for that day's link pass (spec §6.1, ADR-0003).

### Step 5 — Recreate the container

- [ ] `docker compose up -d --force-recreate upmovies-backend` (or Coolify's redeploy).
- [ ] `printenv | grep -E 'HEALTHCHECK_SWEEP|SWEEP_'` **inside the container** to confirm — read the
      running env, not the compose file. A long-running container holds the env it was created with,
      so the two can disagree for hours.

### Step 6 — Verify

- [ ] `alembic current` matches head — the release carries `6fa399bfcd04` (widens
      `ck_ingest_run_kind` to admit `'sweep'`).
- [ ] Trigger the sweep once by hand (run the scheduled task from Coolify) rather than waiting for
      07:00. Expect a **~45-minute** run: ~7,519 person requests plus the refresh set.
- [ ] `/admin/runs` shows a **`Sweep`** row with its own kind, and a `detail` line reading
      `enumerate: … seeds, … candidates, 0 admitted, skipped N (already_known=…, no_tranche=…); refresh: …/… refreshed (… dormant), … failed`.
  - `0 admitted` is **correct** for this release — see §3.
  - The skip breakdown names one reason per candidate, in the `tmdb` stage's format. With every
    flag closed, `no_tranche` should account for everything that got as far as being judged —
    a `corroboration=…` term appearing while admission is off would mean the gates are being
    asked in the wrong order.
  - `no_tranche` is roughly what the sweep would admit with a tranche open, but the figure M4's
    corroboration threshold is actually read off is the attachment histogram in the sweep's logs
    (`attachments {1: …, 2: …}`), which no current setting narrows.
  - A run that enumerated fine but shows `refresh: 0/0` is the failure mode this whole design is
    watching for (spec §6.2) — investigate before opening any tranche.
- [ ] The healthchecks.io sweep check goes green after that run.
- [ ] The daily pipeline still runs clean the next morning, and the retrieval-health trend on
      `/admin/runs` hasn't moved — nothing was admitted, so it shouldn't have.

## 3. Deliberately NOT part of this deploy

**Admission stays off.** `SWEEP_ENABLED`, `SWEEP_ADMIT_DIRECTORS`, `SWEEP_ADMIT_WRITERS` and
`SWEEP_ADMIT_CAST` all default `false` in code. This release ships the M2 state on purpose: the
sweep runs, reports what it would admit, and admits nothing.

`SWEEP_CORROBORATION_THRESHOLD` (NEU-1086) is the fourth dial and defaults to `1` — the identity
value, so the bar is status plus a seed-grade role and nothing else. It is a **placeholder**: NEU-1087
sets it from the discovery probe. Leave it alone here. When the directors tranche is opened, open it
on its own — flipping a tranche and raising the threshold in the same step is the one thing spec §7.4
is written to prevent, because the resulting precision number tells you nothing about which change
caused it.

Opening a tranche is its own decision with its own gates (spec §7.1, §7.4):

- NEU-970's pre-expansion baseline must be collected first — it is a **hard blocker**, since the
  post-expansion comparison has nothing to compare against without it.
- The ramp is directors → writers → top-5 cast, one tranche at a time, so a precision drop names
  the grade that caused it.
- The retrieval T/K retune is a ticket in this project, not a follow-on — cap saturation at K=25 is
  the number to watch as the expansion lands.

Do not fold any of that into deploy day.

## 4. Rollback

| Symptom | Move |
|---|---|
| The sweep is misbehaving or too expensive | Disable the scheduled task in Coolify. No redeploy, no data change; nothing was admitted, so nothing needs unwinding. |
| Precision collapses after a tranche opens (post-v0.3.0) | `SWEEP_ENABLED=false` + container recreate. Dormancy then drains the working set on its own — nothing is deleted (spec §7.3). |
| The migration must come out | `6fa399bfcd04`'s downgrade **fails loudly** if any `sweep` run has been recorded, by design: an operator rolling back decides what happens to that run history rather than losing it silently. |

## 6. Ramp log

_§3 says admission ships off and that opening a tranche is its own decision. This is where the
decisions actually taken get written down — the flags are Coolify UI state, so without this
section the only record that a grade is open is the running container's `printenv`._

| Grade | Flag | Opened | First sweep with it open | Admitted |
|---|---|---|---|---|
| directors | `SWEEP_ADMIT_DIRECTORS=true` | 2026-08-11 | 2026-08-11 04:20 UTC | 639 |
| writers | `SWEEP_ADMIT_WRITERS=true` | 2026-08-12 | 2026-08-12 07:00 UTC | 407 total, **138 writer-only** |
| top-5 cast | `SWEEP_ADMIT_CAST=true` | 2026-08-14 (~20:15 UTC) | 2026-08-15 07:00 UTC (pending) | — |

`SWEEP_ENABLED=true` throughout. `SWEEP_ADMIT_CAST` had no Coolify entry at all and fell back to
the code default `false`; opening it was therefore a **new** UI entry, which per the Coolify
shadowing rule (CLAUDE.md) is the case that does reliably arrive at the value you type — and it
did: `SWEEP_ADMIT_CAST=true` verified on the redeployed container
(`upmovies-backend-m23utbof9z9l4jrm74k400io-201507493690`, created 2026-08-14 20:15 UTC),
alongside directors, writers, `SWEEP_ENABLED`, and K=47 unchanged.

**Writers, 2026-08-12.** The gate — retrieval health green on directors — was met by the
01:50 UTC reading: n=215, saturation 2.79%, zero-candidate 0.93%, no breach. That reading is
also the K=35 calibration baseline recorded in `link/retrieval/health.py`, and it is
directors-only by construction, taken before this flip admitted anything. The flip itself
predates the 07:00 sweep. Catalog after it: 2,775 films, 1,112 undated.

**Cast is gated on a reading that now exists, and it was not green.** The gate is retrieval
health green on *writers*. The first full-day backlog over the post-writers catalog — 2026-08-13
09:05 UTC, n=184 — came back a **soft breach**: saturation 7.61% against the 5% warn rate,
2.7x the K=35 directors-only baseline, with zero-candidate at 0.00% (the hard tier was never in
play). Opening writers gave back roughly the whole benefit of NEU-1088's K=25→35 retune at the
same K.

That breach is the soft tier working as designed — it scheduled the third T/K pass rather than
leaving the drift to be found by hand. **NEU-1135 is that pass**: K moves 35 → 47, T holds at
0.5, and the warn rate is reaffirmed at 5%. Sequence from here:

1. ~~Merge NEU-1135, deploy, and make the Coolify change in §5.~~ **Done 2026-08-13** — PR
   #258 merged as `5f7d2b7`, K=47 confirmed live on the running container.
2. ~~Wait for the **2026-08-14 09:05 UTC** reading over the post-writers catalog.~~ **Green,
   2026-08-14 09:11 UTC**: n=253, saturation **2.77%** against the 5% warn rate,
   zero-candidate 0.00%, mean candidates 18.53, no breach. The 07:00 sweep ran first as
   intended (118 admitted, `no_tranche=2729` — that skip bucket is the cast tranche's
   backlog), so the reading covers the larger catalog. K=47 held the post-writers catalog at
   the K=35 directors-only baseline of 2.79%, slightly above the ~2.1% projection.
3. ~~Only then flip `SWEEP_ADMIT_CAST`~~ **Done 2026-08-14 ~20:15 UTC**, inside the window
   between the 09:11 reading and the 08-15 07:00 sweep. Catalog at the flip: **3,181 films,
   1,495 undated**.
4. **← we are here.** The **2026-08-15 07:00 UTC** sweep is the first with cast open, and the
   **09:05 link run** is the reading that measures it — the first one covering the cast grade
   and nothing else new.

**Flip in the window between a reading and the next sweep.** The sweep runs 07:00 UTC and the
link run that measures runs 09:05, so a flag set the evening before admits its grade two hours
before the reading — which then covers two grades at once and measures neither. The safe window
is the ~22 hours from 09:05 UTC to 07:00 UTC the following day. Same reasoning as `config.py`'s
note on the tranche flags; it is written in both places because one is where the rule is decided
and the other is where someone stands with the Coolify UI open.

Expect the cast flip to **breach the retrieval soft tier**, by design — that breach is what
schedules the **fourth** T/K pass (NEU-1135 was the third). `health.py` is explicit that the
linear ~5.6% projection is a floor rather than an estimate, so do not read a near-miss as the
tranche having been cheap.
